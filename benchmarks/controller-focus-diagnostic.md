# Matched passive controller focus trace

Purpose: identify the controller involved in the proven OS-focus/UIA discrepancy, and distinguish an explicit Bowser COM MoveFocus request from a focus transition without such a request under complete trace coverage. No-request evidence cannot exclude other native SetFocus, activation, visibility or WebView/runtime side effects. No focus repair, delay, retry, SetValue change, setText change or document-wide key observer is added.

The existing isolated diagnostic-interaction opt-in creates immutable tracing contexts containing only a log, a fixed view label, the actual tab when relevant and a unique per-process controller ID. Contexts hold neither App nor controller/host references. Chrome and content controllers get passive GotFocus/LostFocus callbacks; registration start and each original result are logged. Unknown/failed registration, missing identities or unmatched MoveFocus request/result invalidate attribution. Known toolbar/tabs/rail/content participants are required, with popup/settings required only when retained surface evidence shows they opened. Creation is NOT callback coverage start: no earlier absence is inferred. Both original MoveFocus sites remain single calls with their unchanged original result/error behavior, with fixed call-site names, before/after observations and normalized Rust success0 or original failure HRESULT. No new COM operation occurs in a focus callback.

CSV schema is unchanged. For the new controller-focus events ONLY, navigation_id means controller ID, not document navigation ID; tab_id is the associated content tab (0 for fixed chrome), view is a fixed label, pid is the observed native focus HWND owner, count is that HWND and private_bytes is zero. A separate interaction_focus_foreground row records the foreground HWND/PID for the same controller, and interaction_focus_hresult records numeric normalized result codes. Zero HWND is unknown. GetFocus/GetForegroundWindow are read-only local Win32 observations at log time, not atomic with the initiating event or evidence of exclusive HWND ownership. Shared/proxy HWNDs are not assigned a receiver by class. The content observer is registered after the existing product GotFocus callback, which may itself cause focus activity: sampled HWND is the state at observer delivery, not necessarily the event's initial owner. Callback ordering and observer overhead can perturb timing; OFF/ON rows remain separate, with no overhead subtraction or primary gain reuse.

Both reference and candidate are rebuilt with identical instrumentation, toolchain, flags and generated UI; the reference restores only src/blocker.rs and removes src/blocker/registration.rs. CI records actual build source/tree/hash/bytes and asserts those are the only tree differences. Original46ee,9862 and primary result artifacts stay immutable. One fixed small cohort has two alternating four-arm pairs, fresh/reused,16 planned rows, with ordinary updater OFF, fixed pre/post hashes and confirmed process drain. Every failure remains; no retry-to-green or blind sample expansion. The OS-focus harness remains passive at fixed input boundaries. SetText overwrite remains outside this slice.
