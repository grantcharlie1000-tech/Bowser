# Bowser 0.0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

**Goal:** Deliver a lean x64 Windows browser with one native input and one WebView2 viewport, plus reproducible performance measurements against Edge and Chrome.

**Architecture:** Keep Win32 windowing, search/navigation, WebView2 hosting, and measurement in separate Rust modules. Check for the Evergreen runtime without starting it, then initialize an isolated WebView2 process group only on the first submitted destination. Keep the app blank and idle before that request.

**Tech Stack:** Rust 1.99 stable, windows 0.62 Win32 bindings, webview2-com 0.39.1 direct WebView2 COM bindings, url crate for URL parsing/encoding, PowerShell 5.1 benchmark harness, Evergreen WebView2 runtime.

**Spec:** docs/superpowers/specs/2026-10-08-bowser-phase-0-design.md

## Global Constraints

- Target x64 Windows; use Rust and native Win32 controls.
- Use the system Evergreen WebView2 runtime and a Bowser-specific LocalAppData profile.
- Start with an empty window; do not load a home page or search engine on startup.
- Do not add Electron, React, browser-based application UI, or a heavyweight UI framework.
- Keep WebView2 sandboxing, site isolation, and security updates enabled.
- Deny permissions, cancel downloads, keep web popups inside the one viewport only when user-initiated and HTTP(S), and block external protocols.
- Do not run app telemetry or idle polling; benchmark instrumentation runs only when explicitly enabled.
- Record measurements as observed; report battery power as unmeasured if no reliable per-process source is available.
- Deliver the smallest complete 0.0.1 only; do not add conventional browser features.

## Review Focus

1. A typed unsafe or unsupported scheme such as javascript, file, data, or mailto never reaches WebView2; benchmark file loading is accepted only under the local fixture directory and only with explicit benchmark flags.
2. A missing runtime or unwritable user-data directory produces a helpful error and does not crash.
3. A popup, download, permission request, or external protocol is denied or contained by the documented safe policy.
4. Closing during active navigation calls the WebView2 close API and leaves no Bowser-owned WebView2 process behind.
5. Unicode, whitespace, malformed URLs, and invalid search-provider configuration never produce a malformed or unsafe destination.

## Integration Choice and Fallback

The first integration is webview2-com 0.39.1 because it exposes current WebView2 COM callbacks without bringing in a windowing framework. It uses unsafe bindings, so the engine module is its safety boundary. The older high-level webview2 crate (0.1.4, released 2021-10-20) is simpler at the call site but uses legacy winapi/winit dependencies and is not a good base for a browser that must retain current WebView2 behavior.

Before the full adapter, compile and launch the smallest possible native window plus WebView2 environment using the selected crate and installed MSVC toolchain. If that path requires a large framework or cannot produce a functioning environment/controller, pause before adding application behavior and compare a direct windows-rs generated binding against the small native webview library at https://github.com/webview/webview. Any switch must keep a native Win32 shell, preserve the Evergreen runtime and security defaults, and report its added native/C++ dependencies and binary/runtime footprint.
