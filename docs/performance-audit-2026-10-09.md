The strongest route is to reduce unnecessary website work, manage the loaded WebView's lifecycle, and optimize the measured WebView2 creation phase. The native Rust/Win32 shell is already small. The evidence does **not** establish a change that will make all browsing 60% faster and 20% lighter. These are proposed experiments, not achieved improvements. **The main memory opportunity is inside WebView2 and website content.** The empty window is one process using about 9.4 MiB working set and 1.8 MiB private/commit. Once a page loads, there are seven processes. Recalculating the per-process records shows Bowser itself at about 15.4–15.5 MiB working set and 2.8 MiB private/commit. Even eliminating the host process's entire loaded-page allocation would save only about 4–5% of summed working set and 1.6–2.4% of private/commit. Host allocation cleanup, dependency pruning, or compiler tuning cannot supply the requested 20% RAM saving on their own.

The recommended experiments, in order, are:

1. **Pin the executable and attribute creation before optimizing it.** [Start-Bowser.cmd](C:/Users/charlie/Documents/ChatGPT/Bowser/Start-Bowser.cmd:3) launches `target/release/bowser.exe`. [run.ps1](C:/Users/charlie/Documents/ChatGPT/Bowser/benchmarks/run.ps1:22) also prefers that executable. It is the 666,112-byte build hashed `c1a8b654574a4df64890a39c2a5898bf06fceda7ab8ff25735cc352bc5b1a0b6`. The newer `target/x86_64-pc-windows-msvc/release/bowser.exe` is 670,720 bytes, hashed `c3601a5c557e0b14d36c6bfb4211281527b48611f3535f11e389418b31088e54`. Current source includes profile, environment, controller, and configuration timing events; the final benchmark logs contain none of those phase events. Thus the old benchmark establishes the launcher baseline, but cannot attribute the newer source's creation stages. Measure the newer executable explicitly, retaining its hash and phase events. Optimize the dominant demonstrated stage, using ETW/WPA if the delay is inside runtime process startup or disk work. Do not assume policy-handler registration is expensive. [Current creation probes](C:/Users/charlie/Documents/ChatGPT/Bowser/src/engine/webview2.rs:168), [Microsoft profiling guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)

2. **Reduce avoidable requests and scripts on real websites.** This is the best candidate for improving active browsing speed and memory together. Current source installs navigation and safety handlers, but no custom resource filters or explicit tracking-prevention policy. Defaults may already provide Balanced tracking prevention; this is not evidence that tracking prevention is absent. Compare the existing profile level with Strict first. If necessary, test a maintained, selective list of known advertising/tracking requests through `WebResourceRequested`, with bounded in-memory decisions and narrow filters. Blocking requests before download/execution can avoid their downstream work; that benefit is an inference to test, not a measured percentage. Preserve essential page scripts and provide recovery for broken sites. The local fixtures contain no third-party requests, so this approach cannot improve their scores through request removal. [Profile API](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2profile3), [Request interception API](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/webresourcerequested)

3. **Use a deliberate minimized-window resource policy.** [window.rs:148](C:/Users/charlie/Documents/ChatGPT/Bowser/src/win32/window.rs:148) handles `WM_SIZE` as resizing, without a minimized-state resource transition. [webview2.rs:429](C:/Users/charlie/Documents/ChatGPT/Bowser/src/engine/webview2.rs:429) sets the controller visible at creation, and the engine adapter offers no suspend/resume operation. A candidate policy is to hide the controller and call `ICoreWebView2_3::TrySuspend` when minimized, then restore it on return. Suspension is best-effort and requires an invisible controller. Check successful completion and exceptions such as active media; test state and restoration responsiveness. This targets inactive resource use, not visible-page readiness. [Microsoft suspension API](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_3)

   Where background scripts/network must continue, test `ICoreWebView2_19::MemoryUsageTargetLevel` Low while inactive and explicitly restore Normal on activation. Choose that policy or suspension; do not layer both indiscriminately. Low can swap memory to disk and affect responsiveness, so lower working set alone is insufficient evidence of a better result. [Microsoft memory-target API](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_19)

4. **Treat preparation during typing as an optional product tradeoff.** Creating the engine after meaningful address entry could overlap approximately 405–548 ms of measured initialization with typing, making Enter-to-page readiness faster when that overlap is available. It would start spending memory before submission, and would not reduce launch-to-page work or help immediate pasted/submitted destinations. The [existing Phase 0 spec](C:/Users/charlie/Documents/ChatGPT/Bowser/docs/superpowers/specs/2026-10-08-bowser-phase-0-design.md:14) explicitly requires no preloading. This is a potential future change to that requirement, not the recommended default or a proven route to both targets. Do not send searches or speculative destination requests while the user types.

The current architecture already makes several good performance choices: native initial UI; local persistent profile; lazy creation; one retained engine; weak application references in callbacks; and a blocking Win32 message loop without background sampling. Preserve those. A proposed release-build LTO experiment is low priority: it affects the tiny host and cannot remove the runtime's memory floor. Microsoft recommends retaining GPU acceleration and Evergreen, and cautions against shipping browser flags as durable production configuration. Disabling GPU, site isolation, or security checks is not a credible joint optimization. [Performance guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance), [Browser flag support policy](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/webview-features-flags)

**Proof of the target requires a workload-specific comparison.** Keep the current local fixtures unchanged as correctness and fixed-content controls. Add representative real browsing journeys, including a minimal page, search, a script-heavy site, cross-origin navigation, back/forward, and media. Measure launch-to-ready, Enter-to-ready, subsequent navigation, and restoration separately. Compare one candidate at a time with the same pinned executable/runtime conditions, randomized paired runs, fresh/reused profiles, and both ordinary and constrained-memory hardware.

For active memory, the target is approximately 23–35 MiB less private/commit and 58–72 MiB less summed working set on these fixtures. Sample the whole process group at equal times and compare peaks as well as settled values. Validate the private/commit proxy against native process memory counters: the current harness reads `Win32_Process.PageFileUsage` in KiB, while summed working sets can double-count shared pages. Also collect process roles, paging/hard faults, CPU time for each journey, and GPU memory. [Counter definition](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process)

For average session resources, report the active and inactive time mix. For example, spending half a session minimized with a **measured** 40% RAM reduction in that state would yield a 20% time-weighted reduction, assuming active RAM is unchanged. That is arithmetic, not an observed suspension result. It does not prove 20% lower active RAM. Static idle CPU is already approximately 0.03–0.10%; active CPU and energy need separate workloads and measurement. The existing data contains no battery-energy evidence.

The title marker plus two frames is a useful controlled fixture proxy, not proof of interactive readiness on arbitrary sites. The blank-submit result includes synthetic text entry and ends at Enter, so it cannot establish search-result speed. Existing samples use 15.9 GiB RAM, static local content, five trials per condition, and uncontrolled Windows file caches. No new runtime benchmark or optimization was run in this audit.

The next investment should therefore be **accurate attribution, selective reduction of website work, and inactive lifecycle management**. A blanket 60% speed and 20% resource claim remains unproven; the table above makes the exact acceptance thresholds reviewable.
